# 逐題人工審閱頁

一個跑在本機的小網頁，把待審的東西一題一題攤開，人只要按「可以／要改／存疑」並寫意見。

這是這套工具箱裡**最被低估但最常用**的一塊。前面三套流程都會產出「候選」，而候選必須有人看過才能變成內容——審閱頁就是那個關卡。目前實際跑過三份：600 題考古題的引註查證、365 題模擬題的內容審訂、75 則版本落差筆記的結論複查。

---

## 為什麼不是用試算表

一開始真的是用試算表。三個問題讓它撐不住：

1. **看不到上下文。** 要判斷一題詳解對不對，你得同時看到題幹、四個選項、正確答案、現有詳解、教科書原文。塞進試算表的一列就不能看了。
2. **圖沒辦法看。** 附圖是要一起審的。
3. **審到一半會忘記審到哪。** 而且改了什麼、為什麼改，隔一天就想不起來。

---

## 基本結構

```
待審資料（唯讀）  ──>  本機 HTTP server  ──>  瀏覽器逐題顯示
                             │
                             └──>  判決檔（另存，可隨時重跑）
```

三個設計決定，每一個都是踩過才定下來的：

### 原始資料永遠唯讀

審閱頁**不會寫回原始資料**。判決存在另一個檔案裡，用項目 id 當 key。

好處是審查過程中隨時可以重跑上游流程、重新產生候選，而已經做過的判決不會被蓋掉。壞處是套用判決要另外做一步——但那一步應該是刻意的、可檢查的動作，不該是審閱頁的副作用。

### 判決檔用 id 當 key，不用順序

一開始用「第幾題」當 key，後來刪掉幾題重複題，整份判決就全部錯位了。

改成用項目自己的 id 之後，**刪題時刻意不重編號碼、留空號**。看起來醜，但比起判決檔錯位便宜太多。

### 可以中斷續做

每次按下判決就立刻寫檔。重新整理、關掉重開、隔天再來，都從沒審到的地方繼續。

順帶一提：審閱頁應該要有「只看還沒審的」這個選項。600 題的清單如果每次都從第一題開始捲，人很快就不想審了。

## 複審模式

審完、改完之後，還需要一個**驗收**的步驟——人要確認「你照我的意見改出來的東西，我接受」。

做法是拿改動前的備份當基準，左右並排顯示原版與新版，每一項可以按「接受」或「退回」。

這一步很容易被省略，但省掉的代價很具體：在版本落差筆記那份審查裡，**28 則舊條目複審之後有 17 則被推翻**。如果沒有複審，那 17 則錯的內容會一直留在站上。

---

## 實作上的小事，但會影響人願不願意審

- **一個項目一個畫面**，不要做成長長的清單。人要能專注在一題上。
- **鍵盤操作**。滑鼠點 600 次和按 600 次鍵，體感差很多。
- **進度要看得到**。「還剩 480 題」比「已完成 20 題」更誠實，也更能讓人決定今天要審多少。
- **意見欄不要限制字數**，也不要強制填。多數項目按一下就過了，少數需要長篇說明。
- **同時開多份審閱頁時記得換 port**。實際上我們三份審閱同時在跑，各佔一個 port。

---

## 需要什麼輸入

- 一份待審項目的清單（JSON 陣列即可），每項有穩定的 id。
- 每項要顯示的欄位——題幹、選項、答案、詳解、圖片路徑等等，依用途而定。
- 選用：上游流程產出的「候選」，例如搜尋到的原文段落、裁出來的圖。

輸出是一份判決檔：`{ "<項目 id>": { "decision": "...", "note": "...", "at": "<時間>" } }`。
