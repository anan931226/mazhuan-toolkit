# 實際遇到的問題與解法

這一篇是流水帳，但可能是整份文件裡最有用的一篇——都是真的踩到、真的有代價、最後真的改掉的事。

依性質分成四類。

---

## 一、資料的完整性

### 刪掉的題目重灌之後還在線上

灌資料的腳本寫的是「刪掉即將寫入的那些 id，再寫進去」。看起來合理，直到有一天題庫刪了 5 題重複題——重灌之後線上還是 365 題，而檔案只有 360 題，那 5 題繼續出現在網站上。

**症狀很難察覺**：腳本沒報錯，數字也不會主動跳出來給你看。

**解法**：如果一份檔案就是該資料表的全部內容，那就讓它**真的完全等於**——先刪掉檔案裡沒有的列，再寫入。同時加一道防呆：新內容的列數若少於線上現有的一半就中止，要加 `--force` 才做。否則哪天檔案讀壞了，就會安靜地把線上清空。

### 重灌時欄位被無聲清成預設值

「先刪再插入」的腳本，`INSERT` 欄位清單漏列哪個欄位，那個欄位就會被重設成預設值。不會報錯。

**解法**：加欄位的時候，**三個地方必須一起動**——資料表的欄位、灌資料腳本的欄位清單、前端讀取的地方。少一個就是無聲失效。實際發生過一次：新增的欄位前端讀得好好的，但資料庫根本沒有那個欄位，每一列都是 `undefined`。

但「記得一起動」靠不住，所以後來把它變成會爆的錯誤：**每支灌資料腳本在動任何資料之前，先拿自己的欄位清單去跟資料表實際的欄位比對**。每一欄都必須是「有被寫入」或「有被明確說明為什麼不寫」，否則直接中止。

關鍵是**理由是強制的**，不能只寫一份「忽略清單」：

```python
seed_guard.assert_column_coverage(cur, "chapters",
    writes=["id", "num", "title", "blocks"],
    omits={
        "created_at": "資料庫預設 now()",
        "category_id": "由另一支腳本負責，本檔刻意不碰",
    })
```

因為「為什麼不寫」正是下一個人需要知道的事。上面那個 `category_id` 就是實例——它不是忘了寫，是刻意不寫，而這件事只能靠註解傳達。

**這道檢查必須在任何 delete 之前執行。** 擋在刪除之後等於沒擋。而驗證「它真的在前面」時要小心：**行號不等於執行順序**。有一支腳本的 delete 在第 51 行、檢查在第 70 行，看起來順序錯了——但第 51 行在函式定義裡，實際呼叫發生在檢查之後。用行號比大小的檢查方法自己就差點給出錯的結論。

### 判決檔因為重編號而錯位

審題時用「第幾題」當 key，後來刪掉幾題，整份判決全部對錯人。

**解法**：用項目自己的 id 當 key，**刪除時留空號、不要重編**。看起來醜，但比判決錯位便宜太多。

### 編號是會說謊的標籤

網站上的章節 id 是舊版編號，標題才是新版編號，六十篇裡有五十九篇對不上。任何「從 id 推章號」的程式碼都會錯。

**解法**：**認內容，不認編號。** 而且 id 一旦被別的資料拿來當外鍵（錯題、收藏、作答紀錄），就再也不能改了——只能在文件裡大聲寫下來。

## 二、部署與驗證

### CDN 快取讓你以為沒部署成功

推上去之後去抓網頁，抓到的是舊檔。於是你開始「修」一個根本沒壞的東西。

實測連續抓四次都是舊的，第五次才換新。

**解法**：驗證線上版本一定要繞快取，而且要**比對檔案大小或雜湊值**，不要只看「網頁打得開」。

```
curl -H 'Cache-Control: no-cache' "https://.../index.html?cb=$(date +%s)"
```

這個陷阱的失敗方向特別糟：它讓你去改一個正確的東西。

### 提交了一份不是自己建置的產出

多個工作階段共用同一個工作目錄時，別人可能為了隔離未定案的改動，在工作區留下一份刻意合成的建置產出。你順手提交了它，訊息寫「某功能上線」，但那份檔案裡根本沒有那個功能。

**解法**：**提交建置產出之前自己重新建置一次**，並且 `grep` 那份產出，確認這次宣稱新增的符號真的在裡面。建置腳本成功不代表內容正確。

配套的另一半（對面那個工作階段要做的）：**不要在共用工作區留下不是從當前真實來源建置的產出**，要建就建到暫存區。兩邊各做一半才補得起來。

### 語法檢查通過不代表跑得起來

`node --check` 只驗語法。真正會炸的是頂層執行時的未定義變數。

**解法**：用一個最小的 DOM stub 實際把整份程式跑一遍。這台機器跑不了瀏覽器自動化，所以另外做了一套「把打包好的 IIFE 尾巴換成匯出、再用真實線上資料呼叫內部函式」的測試方式，最後累積到 150 多項斷言。

## 三、使用者看得到的東西

### 「記住做到哪裡」記錯了東西

原本存的是「你在這一批題目裡停在第幾個位置」。題庫長大到一千多題、又加了跳題功能之後，這個記錄幾乎沒用了：換一個範圍就失效，跳過題就失準。

**解法**：把「記位置」換成「記題目」。每一次作答本來就會永久記下來，所以「這個範圍你做過幾題、還剩幾題」可以直接算出來，不需要任何額外的儲存。再加一個「只出沒做過的」開關，那才是真正的「繼續上次」——它不綁批次、跳題也不會失準。

**通則**：要記錄狀態之前先問「這件事能不能從既有資料算出來」。能算出來的就不要存。

### 並列的說明裡，省略等於否定

三條路徑的行為不同，說明也寫成三段。其中兩段寫了「作答紀錄照常留著」，第三段沒寫——因為那段的作者（我）沒想到要寫。

結果是：讀者看過前兩段再看第三段，會反推成「這一條不會留」，而**剛好推反**。

**解法**：並列的說明要逐項對齊——同一個面向，要嘛每段都講，要嘛每段都不講。後來加了測試直接斷言三段都必須提到作答紀錄怎麼處理。

### 沒人知道有那些功能

「只出沒做過的」「結算成績」「落點可以點開」「星星可以收藏」——做了但藏在介面裡，不講就等於沒做。

**解法**：一個「關於本站」頁面，兩塊：**這個網站怎麼用**，和**做了什麼更新**。更新紀錄寫給讀者看，不要出現檔名或函式名；日期取自實際上線紀錄，不要憑印象。

### 自己輸入的身分會長出髒資料

身分讓使用者自己打、沒有任何格式限制，結果資料裡混進了暱稱。真要拿作答統計對外講的時候，得先花力氣清。

**解法**：**越早加格式限制越好**，因為要清的資料只會越來越多。同時一律轉大寫，免得同一個人的大小寫變成兩個人。既有的舊值用別名對應過去，並且**連資料庫裡的舊紀錄一起改名**——不改的話同一個人會在統計裡被算成兩個。

## 四、程式碼裡的陷阱

### 位置取值的陣列

一批並行的查詢回來之後用索引取值。**在中間插入一筆新查詢，後面每一個索引都會位移一格，而且不會報錯**——只會讓某個功能安靜地拿到別張表的資料。

**解法**：新增的一律接在最後面，並在程式碼裡寫明為什麼。

### 死欄位會誤導下一個人

有個欄位在改版之後沒有任何地方會讀它，而且兩個寫入點的格式還不一致。目前無害，但下一個人很可能拿它來做事。

**解法**：**確認沒有讀取點就直接拿掉**，不要留著加個註解說「這個沒在用」。同樣的判斷後來又套用了一次：另一個欄位的唯一讀取點被刪掉之後，那個欄位也跟著移除。

### 一個旗標管兩件事

有個旗標同時控制「要不要存進度」和「要不要顯示分數」。等到出現「要計分但不要存」的需求，就得拆開。

**解法**：拆成兩個旗標，各管一件事。後來又加第三個的時候就沒有再糾纏了——雖然當下三者的值完全相同，還是分開寫。

### 判斷「只存在線上的資料」時只比對了檔案

想找出「資料庫有、本機檔案沒有」的資料，於是比對了所有來源 JSON。結論說某一列只存在線上——**錯的**。它寫死在灌資料腳本的常數裡，完全可以重建。

**解法**：來源不只有資料檔，**還有腳本裡寫死的常數**。這個錯誤是另一個工作階段指出來的，也是為什麼多一雙眼睛有用。

### `while read` 會漏掉最後一行

檔案結尾沒有換行時，`while read` 讀不到最後一筆。一次批次刪除因此少刪了一個檔案。

**解法**：批次操作**做完一定要重新驗一次數量**，不要相信「我下了指令所以它做完了」。

### 不遞迴的列目錄

盤點圖片時用了不遞迴的方式列目錄，於是完全沒看到子目錄裡的 79 個檔案，還把兩個分類各報成「1 張」。

**解法**：任何盤點都要先確認**你數的範圍等於實際的範圍**。這次沒有造成損害純粹是運氣——刪除清單只取自頂層。

### 以為是強化，其實讓整個機制靜默失效

做了一道存取控制：一張公開可讀的名單表，前端查名單決定放不放行。名單讀不到就一律放行（fail-open），免得一次網路失敗把所有人鎖在外面。

接著有人注意到名單裡有個「這組給誰」的備註欄，公開可讀等於把名冊攤在外面，於是想用**欄位層級的讀取權限**把那一欄鎖起來。

**這會讓整道門安靜地消失。** 前端查詢用的是 `select=*`，而只要有任何一欄沒有讀取權限，**整個查詢就失敗**——不是少回傳那一欄，是整筆失敗。失敗被 fail-open 的 catch 接住，名單變成空的，於是「名單還沒建立」，門不生效。

**外觀完全正常。** 沒有錯誤訊息，網站照常運作，只是誰都進得來。

**解法**：那個隱私問題不能靠權限解決，只能靠使用方式——在介面上明講「這一欄是公開可讀的，不要寫姓名」，並且把原本寫著「這組給誰」的提示字換掉，因為那等於在邀請使用者把名字打進去。

**通則**：**動權限之前，先去讀實際發出的那一行查詢。** 只看資料表的定義看不出這個問題。而且 fail-open 的設計會把「權限設錯」轉譯成「功能靜默關閉」——那正是 fail-open 的代價，選了它就要記得它會吃掉哪一類錯誤。

（這一條是另一個工作階段在動手之前先讀了線上程式碼才發現的，改動根本沒有送出去。）

## 一個貫穿全部的原則

上面幾乎每一條都是同一件事的不同面向：

**安靜失敗比大聲失敗貴得多。**

欄位被清成預設值、索引位移一格、判決檔錯位、抓到快取的舊檔、漏掉最後一行——沒有任何一個會報錯。它們都是等到有人發現內容不對，才回頭找了很久。

所以值得投資的不是「不要犯錯」，而是**讓錯誤發得出聲音**：做完就重新數一次、部署完就繞快取比對、加欄位就檢查三個地方、寫測試直接斷言行為而不是斷言文字。
